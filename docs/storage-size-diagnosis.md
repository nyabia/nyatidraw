# 실사용 프로젝트 저장 용량 진단

상태: 원인 확인 후 root 목록 무손실 압축 구현 및 복사본 검증 완료. 사용자 원본에는 적용하지 않았다.
작품 이름·경로·날짜·이미지는 기록에 포함하지 않는다.

## 측정

닫힌 작품의 별도 복사본에서 redb 테이블을 분석하고 compact했다.
원본의 진단 전후 SHA-256이 같음을 확인했다. 값은 byte 기준이다.

| 항목 | 측정값 |
|---|---:|
| 원본 파일 | 39,456,768 |
| 복사본 compact 후 | 23,334,912 |
| compact만으로 감소 | 16,121,856 (40.9%) |
| root 압축 + 새 DB 재작성 복사본 | 8,712,192 |
| 원본 대비 최종 감소 | 30,744,576 (77.9%) |
| 모든 테이블 stored bytes | 10,846,332 |
| 모든 테이블 fragmented bytes | 7,329,768 |
| 타일 blob payload 합계 | 2,725,794 |
| root 테이블 stored bytes | 7,549,221 |
| stroke 레코드 stored bytes | 382,822 |

- 타일 986개는 모두 압축되어 있으며, 다시 압축해도 동일했다.
- 저장된 root는 113개, history는 128개다. 진단 당시 전체 타일 목록을 root별로 비압축 저장하여
  거의 변하지 않은 목록도 반복되었다. 새 구현은 이 목록을 압축하며, 구조 공유는 아직 적용하지 않는다.
- compact로 줄어든 물리 공간과 테이블의 fragmentation 값은 같은 지표가 아니며
  서로 더해서 추가 절감량으로 계산하지 않는다. compact도 논리적 레코드 중복을 없애지는 않는다.
- 현재 head에 필요한 타일과 과거 history에만 필요한 타일의 바이트는 아직 분리 측정하지 않았다.

## 무손실 개선 검증

새 복사본은 8.31 MiB다. compact만 한 복사본보다도 14,622,720 bytes(62.7%) 작다.
root 값의 canonical 합계 7,545,605 bytes는 저장값 2,840,009 bytes로 줄었다.
위 표의 root 테이블 stored bytes에는 키도 포함되므로 값 합계와 구분한다.

- 정규화한 전체 테이블 레코드가 변환 전후 일치했다. 저장 표현과 알려진 형식 마커만 다르다.
- history 128개를 모두 보존했고, 129개 cursor의 타일·레이어·캔버스 상태를 모두 읽어 검증했다.
- 닫은 뒤 두 번째로 다시 열어 전체 레코드와 cursor를 다시 검증했다.
- 변환에 사용한 scratch 원본은 byte-exact였고, 사용자 원본은 최종 읽기 전용 SHA-256도 같았다.
- workspace all-features 핵심 테스트가 통과했다. 실사용 사본 검증도 별도 테스트 실행 파일에서 통과했다.

이전 파일은 안전한 일회성 alpha 재작성으로 변환하며 원본 backup을 남긴다.
Undo 삭제나 픽셀 정밀도 변경은 없고, 일반 저장/종료 때마다 compact하지 않는다.
단일 작품에서 확인한 용량 감소이며 시작·저장 속도나 모든 작품의 압축률을 보장하는 측정은 아니다.

## Clip Studio 비교의 한계

비교 CLIP은 20,497,001 bytes였지만 내부 해상도·레이어·이력은 조사하지 않았다.
NyatiDraw PNG는 3840×2160 RGBA16, 비교 PNG는 1920×1080 RGBA8이었다.
비교 PNG의 크기로 CLIP 내부 해상도를 단정할 수 없고, 동일 조건 압축 효율도 판단할 수 없다.
NyatiDraw 프로젝트의 타일은 RGBA8이며 PNG의 16-bit 출력과 구분해야 한다.

## 후속 순서

1. current head / 보존 history / root 목록 / DB 할당 공간을 분리하는 진단을 재현 가능하게 만든다.
2. root 목록의 변경 경로 공유가 추가로 필요한지 측정한다. 이번 압축과 일회성 재작성은 완료했으며,
   별도로 열린 속도와 writer 지연을 측정한다.
3. 이후에도 명시적 최적화 또는 안전한 유휴 재작성이 필요한지 검토한다.
   원자적 교체·복구·여유 공간 부족과 실패 시 원본 보존이 gate다.
4. PNG는 별도로 비트 깊이/압축 속도 옵션을 검토한다. 이것을 NTDR 비대화 원인과 혼동하지 않는다.
